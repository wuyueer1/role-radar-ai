# RoleRadar AI｜AI 岗位情报与匹配工作台

**状态：** 产品设计已批准，等待书面规格复核  
**日期：** 2026-07-30  
**目标岗位：** AI 产品经理 / AI 解决方案为主，数据科学与 AI 应用工程为辅  
**作品定位：** 面向 AI 岗位面试的公开 AI coding 作品，同时是候选人本人可以持续使用的岗位筛选工具

## 1. 决策摘要

首版 CareerGraph AI 失败在产品定位，而不是缺少一个接口。它优化了本人现场演示的稳定性，却使用静态策展岗位和 owner-only 托管，导致外部面试官需要 OpenAI/ChatGPT 身份验证，也无法回答“现在有哪些真实岗位、我应该投哪里、需求发生了什么变化”。

重构后的 RoleRadar AI 不再以静态职业路径为核心。它采用：

1. 多来源真实岗位定时更新；
2. 面向 Yueer 匿名画像的可解释岗位匹配；
3. 近 7 天与 30 天的岗位和技能趋势；
4. BOSS 直聘、猎聘等封闭平台的 JD 文本即时分析与职位链接尽力导入；
5. GitHub Pages 公开免登录访问；
6. GitHub Actions 每 4 小时执行采集、分析、验证和发布。

旧版职业图谱只保留为基于真实岗位聚合生成的“岗位簇地图”，不再承担首页主产品价值。

## 2. 目标与非目标

### 2.1 产品目标

- 面试官通过公开链接直接访问，不需要 OpenAI、ChatGPT、BOSS 或其他产品账号。
- 首页直接展示 Yueer 匿名画像对应的真实 AI 岗位结果，不要求访问者先上传简历。
- 每条岗位结论包含来源、更新时间、原始投递链接、匹配分解和简历证据。
- 自动岗位池至少覆盖两个公开或授权来源，并以实际供给为准，不填充虚构岗位。
- 用户粘贴任意 JD 文本后约 2 秒内获得本地匹配、证据与技能缺口分析。
- 用可复现的 NLP、语义嵌入、职位分类、技能抽取和趋势计算展示 AI 工程能力。
- 形成一条三分钟面试演示闭环：市场变化 → 个人机会 → 证据解释 → 即时 JD 验证。

### 2.2 非目标

- 不自动抓取需要登录或明确禁止第三方访问的 BOSS/猎聘接口。
- 不承诺 BOSS/猎聘链接一定能读取；JD 文本粘贴是保证可用的导入方式。
- 不做登录、账户、支付、通用简历上传、多人协作或长期用户数据存储。
- 不代替原招聘网站接受申请，不自动投递，不模拟用户登录。
- 不把定时快照描述为真正实时数据；产品文案统一使用“每 4 小时更新”或“最新岗位快照”。
- 不输出未经原始 JD 支持的薪资、签证、地点、经验或公司判断。
- 不提供招聘市场预测；趋势只描述已采集样本的历史变化。

## 3. 用户与核心场景

### 3.1 主要用户

- **外部面试官：** 在三分钟内判断候选人是否具备产品判断、数据工程、AI/NLP、解释性和前端交付能力。
- **Yueer：** 定期查看真实 AI 岗位、筛选优先投递对象，并分析 BOSS/猎聘等平台上发现的 JD。

### 3.2 首次访问

页面载入后直接展示：

- 最新成功更新时间与数据源健康状态；
- 默认市场范围为中国大陆、香港、新加坡和明确标注的亚太远程岗位，访问者可以切换到全部地区；
- 当前有效岗位数与近 7 日变化；
- 最匹配岗位、增长岗位簇与热门技能；
- 默认选中的第一条岗位及其匹配证据；
- 显眼但不打断阅读的“分析一条 JD”入口。

访问者不需要先理解配置、模型模式或评分滑杆。

### 3.3 三分钟演示

1. 说明页面展示真实、带时间戳的岗位快照。
2. 查看“最匹配岗位”和近 7 日技能变化。
3. 打开一条岗位，展示五维匹配、简历证据和技能缺口。
4. 切换岗位簇地图，解释岗位供给和技能结构。
5. 粘贴一条现场 JD，立即生成本地分析并说明模型边界。

## 4. 信息架构与交互

### 4.1 顶部状态栏

- `RoleRadar AI` 产品名与“把招聘市场变成可解释的个人机会”主张；
- 最近成功更新时间；
- 数据新鲜度：`最新`、`更新延迟`、`数据已过期`；
- 数据源健康入口；
- “分析一条 JD”主操作。

### 4.2 市场概览

四张紧凑指标卡：

- 当前有效 AI 岗位数；
- 近 7 日新增与下架数量；
- 当前供给最多的岗位簇；
- 增长最快的技能及样本变化。

所有百分比同时显示分子、分母或样本量，避免小样本制造夸张趋势。

### 4.3 核心工作区

桌面端使用岗位列表与岗位详情双栏：

- 左侧包含搜索、地点、岗位簇、来源、更新时间和匹配度筛选；
- 列表项显示公司、职位、地点、来源、更新时间、匹配分和三个关键标签；
- 右侧固定展示当前岗位的五维匹配、证据映射、技能缺口、约束、JD 摘要和原站投递；
- 排序支持“最匹配”“最近更新”“增长岗位簇”；
- URL 查询参数保存筛选与选中岗位，使面试官可分享具体视图。

### 4.4 岗位簇地图

地图不再展示手写职业转移边，而由当前真实岗位生成：

- 节点代表 AI 产品、AI 解决方案、数据科学、AI 应用工程、People Analytics 等岗位簇；
- 节点大小代表有效岗位数；
- 节点颜色代表近 7 日相对变化；
- 边权重代表两个岗位簇的技能集合 Jaccard 相似度；
- 点击节点会过滤岗位列表，并在侧栏显示该簇的热门技能和代表公司。

### 4.5 JD 分析器

- 从页面底部抽屉打开，不跳转到聊天页；
- 支持粘贴 JD 正文或职位 URL；
- 对 URL 先判断是否为允许的公开来源；Greenhouse、Lever 等已知公开源可读取，BOSS/猎聘链接只做公开信息尽力读取；
- 链接无法读取时直接提示复制职位描述，不循环重试；
- 文本分析结果包含岗位簇、匹配分解、证据、技能缺口、现实约束与面试准备提示；
- 导入结果只存在当前浏览器会话，不写入市场趋势和公共岗位池。

### 4.6 响应式布局

- 1440×900：指标卡 + 岗位列表/详情双栏为主画布；
- 1024 像素以下：岗位详情变为右侧抽屉；
- 640 像素以下：市场概览、岗位列表、详情依次堆叠；
- 手机端保留搜索、筛选、原站投递和 JD 分析，不隐藏核心功能。

## 5. 视觉设计

视觉方向为“编辑型市场情报终端”，强调可信数据和个人判断，不使用通用紫色渐变 AI SaaS 或重度赛博暗色。

### 5.1 设计令牌

- 纸张白 `#F7F5EF`：主背景；
- 墨黑 `#111821`：主要文字与结构线；
- 电光蓝 `#2D5BFF`：匹配、选中与交互；
- 酸性绿 `#B6F36B`：增长状态，仅与深色文字组合；
- 珊瑚红 `#FF6B5F`：技能缺口、失效与高风险；
- 雾灰 `#E7E9E5`：面板和分隔；
- 数字使用等宽字体，正文使用系统中文无衬线字体，不依赖网络字体。

### 5.2 版式与动效

- 标题具有编辑杂志的尺度，数据区使用清晰网格和高信息密度；
- 来源、编号、时间戳与分析方法始终可见；
- 只使用 160–240ms 的排序位移、数字变化和抽屉过渡；
- 尊重 `prefers-reduced-motion`；
- 不使用背景粒子、持续漂浮、玻璃拟态堆叠或纯装饰性 3D。

## 6. 数据来源与边界

### 6.1 市场范围

- 自动岗位池收集 AI 产品、AI 解决方案、数据科学、AI 应用工程和 People Analytics 岗位；
- 首页默认显示中国大陆、香港、新加坡和明确标注的亚太远程岗位；
- 全部地区视图保留其他真实岗位，用于观察技能结构和展示数据规模；
- 不从地点字符串推断签证、国籍或候选人申请资格；JD 未明确说明时显示“职位未说明”。

### 6.2 首版必选来源

- **Greenhouse Job Board API：** 公开 GET 接口，无需身份验证，提供已发布岗位、更新时间、地点、正文和原始链接。
- **Lever Postings API：** 读取已发布职位；由于浏览器 CORS 限制，在 GitHub Actions 服务端任务中采集。

Greenhouse 和 Lever 都需要具体公司的 board token 或 site name。仓库维护一份人工审核的 `source-registry.json`，每项包含：

- `id`
- `provider`
- `company`
- `boardToken` 或 `siteName`
- `enabled`
- `termsUrl`
- `reviewedAt`

首版使用经过人工核对的目标公司清单，不通过搜索引擎或平台私有接口自动发现公司招聘板。

### 6.3 扩展来源

- Jooble REST API：仅在获得 API key、确认中国岗位覆盖率和展示条款后启用；
- 企业官方招聘页或 ATS feed：每个来源必须建立独立适配器并保留原始链接；
- 其他来源只有在公开访问、授权或条款明确允许的情况下接入。

### 6.4 不接入的来源

- 需要账号 cookie、验证码、逆向私有接口或绕过反爬措施的数据；
- 无法保留原始链接和更新时间的数据；
- 不能明确说明展示授权或来源的数据。

## 7. 系统架构

系统分为四个可独立测试的单元。

### 7.1 数据适配器

每个 `JobSourceAdapter` 只负责：

- 从 `source-registry.json` 接收一个已审核来源配置；
- 拉取一个来源的原始职位；
- 映射为统一字段；
- 返回成功、部分成功或失败的健康状态；
- 不执行匹配、趋势或 UI 逻辑。

### 7.2 标准化管道

按以下顺序执行：

1. HTML 清理和文本规范化；
2. 标题、公司、地点、语言和时间标准化；
3. 通过来源 ID 建立稳定主键；
4. 使用公司 + 标准化标题 + 地点 + 文本指纹进行跨来源去重；
5. 校验原始链接、正文长度和时间字段；
6. 标记当前有效、疑似失效或已下架。

同一输入重复执行必须生成相同规范化结果。

### 7.3 AI 与分析管道

- 双语技能词典抽取显式技能；
- 规则识别经验、学历、地点、语言和工作方式要求；
- `intfloat/multilingual-e5-small` 在 GitHub Actions 中本地生成 384 维文本向量；
- 长 JD 按职责、要求和加分项切分为不超过 512 tokens 的段落，再聚合段落向量；
- 岗位标题、技能和向量共同决定岗位簇；
- 候选人证据段落分别编码，用于岗位与具体简历证据的检索；
- 所有生成结果通过 JSON schema 校验后才能发布。

模型使用 MIT 许可版本并固定模型修订与依赖版本。模型下载由自动化缓存复用；模型不可用时，管道降级为词典、规则和 TF-IDF 分析。

### 7.4 展示层

- React + TypeScript + Vite 构建纯静态公开站点；
- GitHub Pages 提供免登录 URL；
- 当前岗位、趋势、匿名画像和来源健康状态通过版本化 JSON 加载；
- 浏览器只管理筛选、选中岗位、详情抽屉和临时 JD 分析；
- 公开前端不包含任何 API key。

现有 Vinext/Sites 专用 Worker 不进入新公开部署。可复用的 React、CSS、SVG、纯函数评分和可访问性组件迁移到静态 Vite 架构。

## 9. 匹配与解释

五个分量均为 0–100：

1. **核心技能覆盖 35%：** 候选人技能证据对岗位技能要求的加权覆盖；
2. **简历证据强度 25%：** 每条关键要求能否检索到具体经历证据；
3. **语义匹配 20%：** 候选人证据与 JD 片段的 E5 余弦相似度在当前岗位快照中的百分位；
4. **行业与岗位迁移度 10%：** 目标岗位簇与候选人已有研究、人才数据和商业分析经历的邻近度；
5. **现实约束 10%：** 明确写出的地点、经验、语言和工作方式约束。

总分：

`matchScore = 0.35 × skill + 0.25 × evidence + 0.20 × semantic + 0.10 × adjacency + 0.10 × constraints`

只有候选人画像和 JD 都明确提供的信息才进入现实约束分；未知信息使用中性值并标记“未配置/职位未说明”，不能自行推断。明确硬性冲突会显示 `hardBlocker`，即使总分较高也不会进入“优先投递”组。

### 9.1 可解释性要求

- 每项优势必须引用至少一条 JD 要求和一条简历证据；
- 每项缺口必须引用岗位原文或规范化要求；
- 语义分显示为当前岗位池百分位，不伪装成概率；
- 页面显示分析模式、模型修订和分析时间；
- 规则、模型和市场统计的结论使用不同来源标签。

### 9.2 本地 JD 分析

即时导入不把文本发送到远程模型。它使用双语技能词典、规则、TF-IDF/字符 n-gram 文本相关性和相同证据映射生成结果，`analysisMode` 显示为“本地即时分析”。其文本相关性分不与 E5 岗位池百分位混为同一统计，只用于当前 JD 的解释。

## 10. 趋势计算

- 每 4 小时生成当前快照；
- 每个自然日保留一个紧凑聚合记录；
- 7 日趋势比较最近 7 个完整日与之前 7 个完整日；
- 30 日趋势比较最近 30 个完整日与之前 30 个完整日；
- 新增、下架和持续开放岗位按稳定职位 ID 计算；
- 技能热度使用“包含该技能的有效岗位占比”，并同时显示岗位数；
- 样本量少于 5 的技能不显示增长排行；
- 趋势范围明确限定为“本项目已接入来源”，不外推为全市场。

## 11. 自动更新与公开部署

GitHub Actions 工作流：

1. 按 4 小时计划或手动触发；
2. 检出默认分支代码和专用 `market-data` 分支上的最近成功快照；
3. 拉取各来源并生成健康报告；
4. 标准化、去重、AI 分析和趋势计算；
5. 执行 schema、数据质量、单元和构建测试；
6. 成功后把 `current.json`、`history.json` 和 `source-health.json` 提交到 `market-data` 分支；
7. 使用该次数据提交的精确版本构建静态站点并部署 GitHub Pages；
8. 任一步失败时不写入 `market-data`，也不覆盖最近成功的公开站点。

`market-data` 只保存当前规范化岗位、每日聚合历史和来源健康状态；完整历史 JD 不保留。自动化提交使用专用路径和最小 `contents: write` 权限，公开页面显示其数据提交 ID，便于复现。

公开页面的新鲜度规则：

- 距最近成功更新不超过 8 小时：`最新`；
- 超过 8 小时且不超过 24 小时：黄色 `更新延迟`；
- 超过 24 小时：红色 `数据已过期`；
- 单个来源失败时显示来源级警告，但其他来源继续更新。

## 12. 错误处理

- 来源请求超时：有限次数指数退避，之后记录失败并继续其他来源；
- 原始字段缺失：保留职位但标记缺失字段，关键字段缺失则拒绝发布该条；
- 重复职位：保留最完整且原始更新时间最新的记录，保存来源列表；
- 失效链接：连续两次采集无法确认后标记下架；
- 模型下载或推理失败：降级到规则与 TF-IDF，不阻止安全快照发布；
- 浏览器数据加载失败：使用 Service Worker 缓存的最近成功快照；
- JD 文本为空、过短或只有导航噪音：给出可行动提示，不生成分数；
- URL 读取被平台阻止：停止自动尝试并要求粘贴正文。

所有错误信息面向用户说明影响，不显示堆栈、密钥或内部路径。

## 13. 隐私与安全

- 原始简历文件不进入公开仓库或构建产物；
- 匿名画像由审核后的证据摘要组成；
- JD 即时分析默认仅在浏览器内运行，刷新页面后清除；
- 自动化凭据只保存在 GitHub Actions secrets；
- 公开数据仅包含职位展示需要的字段和原始来源链接；
- HTML 正文在进入数据集和界面前进行清理，禁止执行来源脚本；
- 外部链接使用安全的新窗口属性；
- 不采集访问者个人信息，不加入第三方行为追踪脚本。

## 14. 测试策略

### 14.1 数据与管道

- 每个适配器使用固定 API fixture 验证映射；
- schema 验证必填字段、URL、时间和枚举；
- 去重测试覆盖同源更新、跨源重复和相似但不同职位；
- 幂等测试保证相同输入生成相同快照；
- 时间测试覆盖 8 小时和 24 小时边界；
- 故障测试验证一个来源失败时仍可发布其他来源。

### 14.2 AI 与评分

- 双语技能抽取使用中英文 JD fixture；
- 角色分类和岗位簇使用标注样本回归；
- E5 输入前缀、分段和百分位转换使用固定向量测试；
- 五维评分、硬冲突、未知约束和排序保持确定性；
- 每个优势和缺口都必须通过证据完整性断言；
- 模型失败必须进入规则降级并显示分析模式。

### 14.3 组件与端到端

- 筛选、搜索、排序、选中岗位和 URL 状态；
- 岗位详情、来源标签、证据、缺口和原站投递；
- 岗位簇地图筛选与键盘操作；
- JD 文本分析、URL 失败和会话清除；
- 最新、更新延迟、数据已过期和部分来源失败；
- 1440×900、1024×768、390×844 三个视口；
- 无痕或未登录浏览器直接打开公开 URL；
- 键盘焦点、Escape、读屏名称、颜色对比和 reduced motion。

### 14.4 性能

- 生产首屏目标不超过约 2.5 秒；
- 本地文本 JD 初始分析目标不超过约 2 秒；
- 当前岗位 JSON 采用最小字段与压缩，完整正文按需加载或截取；
- Lighthouse 性能、可访问性、最佳实践和 SEO 均以 90 分以上为目标。

## 15. 验收标准

发布前必须同时满足：

- 公开 URL 在未登录无痕浏览器中可直接访问；
- 不出现 OpenAI、ChatGPT 或 Sites 身份验证；
- `source-registry.json` 中每个启用来源都有公司、平台、条款链接和最近审核日期；
- 至少两个真实来源；
- 至少 20 条去重后的当前有效 AI 岗位；不足时扩展公开来源，不使用虚构数据；
- 首页默认地域为中国大陆、香港、新加坡和亚太远程，全部地区视图可以显式切换；
- 每条岗位包含来源、抓取时间和原始投递链接；
- 首页、岗位详情、岗位簇地图和 JD 分析形成完整闭环；
- 匹配结论可以追溯到 JD 与匿名简历证据；
- 4 小时更新、8/24 小时状态和最后成功快照降级通过测试；
- 桌面、平板和手机布局无横向溢出；
- 自动化测试、类型检查、lint、构建和端到端测试全部通过；
- 原始简历、联系方式和任何 API key 不存在于公开产物。

## 16. 从首版迁移

### 16.1 保留

- `Yueer W.` 匿名证据画像；
- 双语技能词典；
- 可解释纯函数评分思想；
- SVG 图谱技术；
- 详情抽屉、焦点管理和响应式基础；
- 自动化测试与面试讲解结构。

### 16.2 替换

- 静态 `dataset` 替换为版本化真实岗位快照；
- 手写角色与职业转移边替换为岗位簇与技能相似度；
- 路径排名替换为真实职位排名；
- 权重实验室替换为市场筛选和可解释岗位详情；
- owner-only Sites 部署替换为公开 GitHub Pages；
- Cloudflare/Vinext 运行时替换为静态 Vite 构建；
- “稳定演示 / Live AI”模式替换为明确的 `E5 岗位池分析 / 本地即时分析 / 规则降级`来源状态。

旧版生产地址不作为最终作品链接；新站验证完成前保留旧版本用于回滚和对照。

## 17. 面试叙事

作品要讲清三层能力：

1. **产品判断：** 发现静态图谱和登录门槛没有真实用户价值，主动重构问题定义；
2. **AI 与数据工程：** 多源采集、去重、双语技能抽取、语义嵌入、岗位聚类、趋势和可解释评分；
3. **交付质量：** 公开部署、数据新鲜度、失败降级、隐私、无障碍、自动化测试和可复现性。

首版失败记录保留在仓库历史中，作为“如何从漂亮 Demo 迭代为真实产品”的证据，而不是隐藏错误。
